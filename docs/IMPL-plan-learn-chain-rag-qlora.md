# Implementation Plan — learn-chain + rag-qlora-loop

## Shared contracts (freeze before any WP starts)

- **SC1 — chain log** (`~/.apex-router/learn_chain.jsonl`): two record kinds, exactly as in the design (`chain`, `stage`). Field names are frozen; all writers go through one helper. Fail-open: any write error logs a warning to stderr and returns, never raises (mirror `route_log.py`).
- **SC2 — bench row**: dict consumed unchanged by `deltas_from_rows`. Keys: `{cell_id, model, arm, reward, prompt_tokens, completion_tokens, cached_tokens, cost_usd, wall_ms, chain_id, topic_id, ts}` where `cell_id = f"{slot}:{task_class}"` (chains) or `f"layer:{task_class}"` (RAG-vs-QLoRA). `arm ∈ {incumbent, candidate}`. Do not invent a parallel row format.
- **SC3 — verdict enum**: `{"ON","OFFERED","SKIP"}` derived solely from `amr.gate` output. No WP may re-implement gating logic.
- **SC4 — verdict/cycle sidecar log** (`~/.apex-router/rag_cycle.jsonl`): `{kind:"cycle", cycle_id, l1_delta, l1_ci, crowding, approved_count, qlora_fired, verdict, dataset_hash, ngram_check, ts}`.

---

## WP1 — Chain instrumentation (P1, no adaptivity)

**Deps:** SC1. **Files:** create `src/apex_router/learn_chain.py`; modify `src/apex_router/cli.py` (`/learn` handler); create `tests/test_learn_chain.py`.

- `ChainLogger(log_path=DEFAULT)`: `log_chain(chain_id, task_class, proposed, executed, edited, shown_rationale)`, `log_stage(chain_id, slot, model, usage: dict, wall_ms, cost_usd)`. All I/O wrapped try/except (fail-open), same pattern as `route_log.py`.
- `run_chain(task, slots: list[Slot], confirm_fn) -> chain_id`: executes slots in fixed order `retrieve→sonnet→opus→kimi`, feeds prior output into next prompt, captures `after_provider_response` usage + `time.perf_counter()` wall.
- CLI: `/learn <task>` renders cold-start default chain + static rationale, prompts confirm/edit, then calls `run_chain`.
- **Acceptance:** run `/learn "explain X"`, edit one slot, verify both record kinds in the JSONL with `edited:true`, `proposed != executed`; kill network mid-run → no exception, partial stage rows present.
- **Guardrail:** log only; reward is never written here.

## WP2 — Post-hoc reward (P2)

**Deps:** WP1, SC2. **Files:** create `src/apex_router/chain_reward.py`; `tests/test_chain_reward.py`.

- `judge_pair(prev_out, cur_out, rubric, judge_model=PINNED_JUDGE) -> float in [-1,1]`: two calls with A/B position swapped; reward = mean of signed scores; rubric seeded from Ornith validation criteria (load from `prompts/judge_rubric.md`, new file).
- `cosine_pregate(prev, cur) -> bool` using existing `embed.py`: if `|cos| >= 0.995` return `skip=True`, reward 0.0, no judge call.
- `compute_rewards(log_path) -> list[bench_row]`: joins chain/stage records, emits SC2 rows keyed `(slot, task_class)`, arm = candidate vs prior stage's output (prior stage is the incumbent baseline within the chain).
- **Acceptance:** synthetic log with one stage whose output equals prior output → judge never invoked (assert via mock); swapped-order mock returning (+0.4, −0.2) yields reward 0.1.
- **Guardrail:** cosine is a skip-gate only; never a reward value. Judge model string pinned in one constant.

## WP3 — Bench cell integration

**Deps:** WP2, SC2/SC3. **Files:** modify `src/apex_router/bench.py` (accept `cell_id` param; do not change `deltas_from_rows` or `amr.gate` signatures); create `scripts/chain_bench.py`.

- `scripts/chain_bench.py --task-class X [--slot S]`: loads reward rows (WP2) or runs live cells via existing `bench.py`, clusters bootstrap by `chain_id` (thread `chain_id` through; dedupe pseudo-replication by `topic_id` — normalize task text, hash → `topic_id`), calls `deltas_from_rows` → `amr.gate`, prints per-slot verdict + three aggregates (paired Δreward + CI, $/Δ, verdict).
- **Acceptance:** fixture rows with known effect → verdict matches hand-computed gate; CI narrows with N; two rows sharing `chain_id` never enter the same bootstrap resample independently.
- **Guardrail:** FDR correction applies across all slots jointly; no per-slot ad-hoc thresholds.

## WP4 — Planner + adaptive confirm (P3)

**Deps:** WP3, WP1. **Files:** create `src/apex_router/chain_planner.py`; modify `cli.py` `/learn`.

- `plan(task_class, eps=0.05) -> list[SlotDecision]`: per slot, verdict from WP3 → ON (include) / SKIP (drop) / OFFERED (listed, not run); cold-start (no rows) → labeled default prior. With prob `eps`, re-include one SKIP slot and mark the chain row `exploration:true`.
- `render_rationale(decisions) -> str`: the design's exact "Planned: … Basis: N chains, +Δ (CI…); X below gate — available if wanted" format, using only the three aggregates.
- `/learn` flow: classifier → `task_class` → `plan` → `render_rationale` (log `shown_rationale`) → confirm/edit → `run_chain` with `proposed`/`executed` recorded separately. CLI flag `--no-rationale` for the anchoring A/B.
- Estimator rule (documented + enforced in `chain_bench.py --estimand proposed-only`): edited chains excluded from Δ estimates, analyzed as separate arm.
- **Acceptance:** seeded fixture where opus slot gates ON and kimi SKIP → plan drops kimi; forcing `--eps 1.0` re-includes it and logs `exploration:true`; edited chain absent from proposed-only estimate.
- **Guardrail:** never pool edited chains into estimates; ε only re-adds SKIP slots, never removes ON slots.

## WP5 — Offline swapped-order replay (P4)

**Deps:** WP3. **Files:** modify `src/apex_router/bench.py` (replay mode); `scripts/chain_bench.py --replay`.

- Log every stage input/output during live runs (extend stage record with `input_hash`, `output_hash`, payloads to `~/.apex-router/chain_payloads.jsonl` — WP1 adds these two fields; note in SC1 addendum). Replay mode re-runs tiers in swapped order or parallel on identical inputs through the existing bench harness, then WP2 rewards → SC2 rows with `replay:true`.
- **Acceptance:** same input run as (sonnet→opus) and (opus→sonnet) produces two valid rows distinguishable by order metadata; gate consumes them like any cell.
- **Guardrail:** live chains stay fixed-order; only replay rows may be used for tier-effect claims (flag in output).

## WP6 — rag-nightly harvester + L1 gate

**Deps:** WP1 (log source), SC4. **Files:** create `src/apex_router/rag_nightly.py`; modify `cli.py` (`rag-nightly [--now]`); `tests/test_rag_nightly.py`.

- `harvest(sources) -> list[Candidate]`: pulls from booksearch index (passages + derived task→approach exemplars, tagged `layer:"RAG"`), `learn_chain.jsonl` high-reward (task, answer) pairs, route/offload failure task_classes (prioritization), codeqa Q&A. De-identify via the same function `record_feedback.py` uses (import it; do not fork). Dedupe by content hash; tag `task_class`, `lineage`, `snapshot_before`. Write to `feedback/staged.jsonl`.
- `l1_gate(candidates) -> promoted`: calls existing `rag_eval.run_condition` on staged-vs-current corpus (snapshot-isolated); promote passers into `feedback/approved.jsonl` via `record_feedback.py`'s writer.
- Emit SC4 cycle row each run (fail-open).
- **Acceptance:** fixture staged candidate that lowers held-out escalation in a mocked `run_condition` appears in `approved.jsonl`; failing candidate does not; book-sourced candidate has `approved_for_training:false`.
- **Guardrail:** books → RAG only; harvester must set `approved_for_training=false` for any book-derived record.

## WP7 — QLoRA trigger (3-part gate)

**Deps:** WP6, WP3. **Files:** `src/apex_router/rag_nightly.py` (function `should_train(history) -> bool`).

- Conditions (all required): approved count ≥ 500; L1 marginal Δreward CI upper ≤ 0.02 for 3 consecutive cycles (read from SC4 history); injected-token share of prompt > 30% on the saturated task_class (measure in `exemplar_inject.py` — add a token-share counter, no behavior change).
- **Acceptance:** synthetic histories: 499 examples → False; saturation only 2 cycles → False; crowding 25% → False; all three → True. Also assert "never fires" path exits 0 with "RAG-only" message.
- **Guardrail:** RAG-only forever is success — no warning/error when gate never fires.

## WP8 — `training/prepare_data.py`

**Deps:** WP6, WP7. **Files:** create `training/prepare_data.py`, `training/probe_general.jsonl` (frozen ~200 prompts), `tests/test_prepare_data.py`.

- CLI: `prepare_data.py --approved feedback/approved.jsonl --out data/<cycle_id>/`.
- Filters `approved_for_training && deidentified`; converts to MLX-LM `{"messages":[...]}` chat format, deterministic train/valid split (seeded); mixes in 10–20% generic-instruction replay buffer (`training/replay_buffer.jsonl`, new).
- **Hard-fail** allowlist of first-party sources; **8-gram contamination scan** of final JSONL against booksearch index → abort nonzero on any hit; writes attestation `{dataset_hash, ngram_check:"pass", counts, replay_frac}` into SC4 row.
- **Acceptance:** plant a verbatim 8-gram from the book index → exit 2, no output dir; record outside allowlist → exit 3; clean run → valid/ train JSONL + attestation.
- **Guardrail:** canary/post-hoc checks are smoke signals only; the allowlist+ngram scan is the proof.

## WP9 — `training/train.sh` + shadow-tag serving

**Deps:** WP8, WP3. **Files:** create `training/train.sh`, `src/apex_router/qlora_serve.py`.

- `train.sh --data <dir> --cycle-id <id> [--dry-run]`: `--dry-run` validates mlx-lm, data, base model, disk; real run: `mlx_lm.lora --fine-tune-type lora --lora-rank {8..16}` cosine LR, early-stop on valid loss, low iters; then `mlx_lm.fuse` → GGUF at **same quant as incumbent** → `ollama create local-candidate:<cycle_id>`. Log rank/iters/valid-loss to SC4.
- `qlora_serve.py evaluate(cycle_id)`: runs the frozen general probe pre/post adapter (reject if drop > 2%) and a bench cell keyed `(layer, task_class)`, arm candidate = shadow tag vs incumbent production config (RAG included) → `deltas_from_rows` → `amr.gate`. On ON: repoint `local` family config to the new tag; keep previous tag for rollback (`qlora_serve.py rollback`).
- **Acceptance:** dry-run on machine without mlx-lm → clear error, exit 1, nothing created; mocked gate ON → config points to new tag and rollback restores prior tag in one command; probe drop 3% → adapter rejected, incumbent untouched.
- **Guardrail:** one serving stack only (path a); the bar is current production config, never the pre-train adapter.
